## Original ask

> it should use jirashastra assess-user story tool to judge whether good test cases will be generated or hallucinated ones due to lack of context in store and overall.

## Problem

Today `generate_test_cases`, `generate_test_plan`, `run_full_pipeline` and `epic_pipeline` (per child) always generate, even when the story is close to empty and retrieval returns nothing. The only guard is a `logger.warn('thin context gathered')` in `gatherContext` (`apps/mcp-server/src/tools/tool-handlers.ts` ~L2552) and a _"Very thin context"_ warning string. Result: plausible-looking but invented cases (fake fields, flows, selectors) get pushed to MT QA Hub and erode trust in the tool.

## Decision: gate on a cheap deterministic readiness check, not on `assess_story`

`assess_story` has three modes, and none of them works as a gate as-is:

* **mode=analyse**: 5-pass LLM, async, takes minutes. Too slow and costly to run before every generation.
* **mode=validate**: the 23-point rubric is format-biased (C01/C04/C05 need "As a… I want… So that…"), so a well-written Task with no user-story format fails it. It also calls an LLM (`runAiValidation`), even though its description says "no LLM spend".
* **mode=score**: measures coverage and pass rates of _existing_ cases, not whether the input is good enough.

So we **reuse the deterministic rule engine behind** `assess_story` (`runRuleValidation` in `@jirashastra/story-validator`) for the content signals only. We do not use its grade.

## Approach

1. **One pure function**: `assessGenerationReadiness(extracted, { additionalContext, contextGaps? })`, in `packages/story-validator`, exported through the barrel. No LLM, no I/O. It returns:
   `{ verdict: 'ready' | 'thin' | 'insufficient', storySignalChars, acCount, failedRules[], contextGaps[], whatToAdd[] }`
2. **Story signal decides whether we block.** It counts the substantive text from description, ACs, `enrichedContent` (linked Confluence, Figma, Drive) and `additionalContext`, after removing template headings and placeholders ("TBD", "see figma", empty AC bullets). It reuses the C03, C06 and AC-quality rule results.
   * `insufficient` means the story signal is below the floor **and** there are no ACs **and** no `additionalContext`.
3. **Context gaps only downgrade a story to** `thin`; they never block. Gaps are the `contextGaps` from `gatherContext`: case-index, app-knowledge, flow-graph, KB. A brand-new feature legitimately has no existing coverage, and `additionalContext` can make up for an empty store. A `thin` result still generates, but the response includes `readiness: 'thin'` plus the gap list, and cases are marked low-confidence.
4. **Run the gate right after** `extractForTenant` and before `gatherContext`. A blocked story then costs no retrieval and no LLM spend. Entry points:
   * `generate_test_cases`, both `execute` and `executeStream`
   * `generate_test_plan`
   * `run_full_pipeline`
   * `epic_pipeline` proceed: an `insufficient` child is skipped with a reason, the same way `epic-plan-registry` skips an empty summary. It does not fail the whole epic.
5. **Blocked response.** Return a structured `errorResult` with code `INSUFFICIENT_CONTEXT`. It lists which rules failed and a concrete `whatToAdd` list, for example: add ACs; pass the Confluence PRD / Figma as `additionalContext` (reuse the existing `mcpHints` link detection); link the MR.
   * It is an error, not an empty success, so CI and pipelines stop instead of pushing nothing.
6. **Override.** `force: true` skips the gate. The skip is logged with `issueKey` and verdict.
7. **Observability.** Log `generation_readiness` (issueKey, verdict, storySignalChars, acCount, gap sources) every time, and emit a usage event on block. This gives us the block rate.

## Calibration (before enabling)

Thresholds live as named constants in the one function. Replay the last ~100 prod generations through `assessGenerationReadiness` offline and tune so that:

* stories whose generated cases were later rejected, or that were never pushed, mostly land in `thin` or `insufficient`;
* well-specified stories are **never** `insufficient` (target false-block rate ≈ 0).

Ship in **warn-only mode** first (compute the verdict, attach it to the response, don't block) behind an env flag. Flip to blocking once the numbers look right.

## Acceptance criteria

* [ ] A story with a summary only (no description, no ACs, no links) and no `additionalContext` makes `generate_test_cases` return `INSUFFICIENT_CONTEXT` with `whatToAdd`. There are no LLM calls and no `gatherContext` calls.
* [ ] The same story passed with a real `additionalContext` (PRD text) generates normally.
* [ ] A well-specified story with an empty case-index and flow-graph generates, and the response includes `readiness: 'thin'` and `contextGaps`.
* [ ] A story with no "As a… I want…" format but a real description and ACs is `ready`, so the rubric's format bias does not leak into the gate.
* [ ] `force: true` bypasses the gate, and the bypass is logged.
* [ ] `epic_pipeline` proceed skips `insufficient` children with a reason and processes the rest.
* [ ] `generate_test_plan` and `run_full_pipeline` apply the same gate.
* [ ] Warn-only mode, controlled by an env flag, attaches the verdict without blocking.
* [ ] Fix the `assess_story` `mode=validate` description: it does call an LLM.

## Tests

* Unit tests (Vitest, `packages/story-validator/test`) for `assessGenerationReadiness`: empty, placeholder-only, AC-only, `additionalContext`-only, non-user-story-format-but-rich, and rich-with-all-gaps.
* Handler tests: generate_test_cases execute and stream return `INSUFFICIENT_CONTEXT` and never call gatherContext or the LLM (spy); `force` bypass; epic child skip.

## Out of scope

* `generate_regression_impact`: it already handles thin stories by pulling child issues and MRs (`regression-impact.content.ts`).
* Adding an LLM-based readiness judgement. Revisit only if calibration shows the deterministic signal misses a real class of bad inputs.
